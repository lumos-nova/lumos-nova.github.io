Spark RDD（弹性分布式数据集）

1. 概念

弹性分布式数据集（Resilient Distributed Dataset，RDD），这个数据集的全部或部分可以缓存在内存中，并且可以在多次计算时重用。RDD其实就是一个分布在多个节点上的数据集合。

1.1 RDD五大特性

  • 可分区的（必备）：Spark RDD是可被分区的，每一个分区都会被一个计算任务（Task）处理，分区数决定并行计算数量，RDD的并行度默认从父RDD传给子RDD。默认情况下，一个HDFS上的数据分片就是一个Partition，RDD分片数决定了并行计算的力度，可以在创建RDD时指定RDD分片个数，如果不指定分区数量，当RDD从集合创建时，则默认分区数量为该程序所分配到的资源的CPU核数（每个Core可以承载2～3个Partition），如果是从HDFS文件创建，默认为文件的Block数
  • 每一个分区都有一个计算函数（必备）
  • 依赖于其他RDD的列表（必备）
  • key-value数据类型的RDD分区器（可选）
  • 每个分区都有一个优先位置列表（可选）

2. 创建方式

2.1 从对象集合创建RDD

  1. 使用parallelize()方法创建RDD
val input_rdd = sc.parallelize(List(1,2,3,4,5))
  1. 使用makeRDD()创建RDD（废弃）

2.2 从外部存储创建RDD

  1. 读取本地文件

  1. 读取HDFS文件
val input_rdd = sc.textFile('hdfs://node1:8020/spark/word.txt')

4. 分区规则

4.1 分区的概念

  • 什么是分区

RDD被划分为多个子集合并分配到不同的节点上，每个子集合就称为一个分区。

  • 为什么要分区

将海量数据划分后，可以并行计算，极大的提高了效率。

  • 分区原则

分区数量应尽量等于CPU核心数

   *(从Hadoop文件中获取数据并生成RDD)
   * @note Because Hadoop's RecordReader class re-uses the same Writable object for each
   * record, directly caching the returned RDD or directly passing it to an aggregation or shuffle
   * operation will create many references to the same object.
   * If you plan to directly cache, sort, or aggregate Hadoop writable objects, you should first
   * copy them using a `map` function.
   * @param path directory to the input data files, the path can be comma（逗号） separated （分隔）paths as a list of inputs
   * @param inputFormatClass storage（存储） format of the data to be read
   * @param keyClass `Class` of the key associated（关联） with the `inputFormatClass` parameter
   * @param valueClass `Class` of the value associated with the `inputFormatClass` parameter
   * @param minPartitions suggested minimum number of partitions for the resulting RDD
   * @return RDD of tuples of key and corresponding value 返回（key,value）形式的键值对
   */

    path: String,
    inputFormatClass: Class[_ <: InputFormat[K, V]],

    valueClass: Class[V],

    // See SPARK-11227 for details.
    FileSystem.getLocal(hadoopConfiguration)

    val confBroadcast = broadcast(new SerializableConfiguration(hadoopConfiguration))
    val setInputPathsFunc = (jobConf: JobConf) => FileInputFormat.setInputPaths(jobConf, path)

        this,
        confBroadcast,

实际分区计算规则

1、看是否指定最小分区数 2、未指定最小分区数，则取默认并行度和2中较小的 默认并行度 – local模式：本机的核心数 –standalone模式/yarn模式：集群中所有的核心总数和2的较大值 3、实际分区数量 1、指定最小分区数 1、goalSize=给定文件大小/最小分区数 2、实际分片大小：splitSize = max(minSize, min(goalSize, blockSize)) 3、minSize默认为1B，blockSize为yarn配置文件中的文件块大小，goalSize为期望分片大小 4、如果 goalSize >= blockSize, 则splitSize = blockSize 5、判断剩余文件大小是否满足分片规则：剩余文件大小/实际分片大小 > SPLIT_SLOP(默认1.1) 6、若满足条件，则继续分片；若不满足则停止分片 7、实际分区数量 = 实际分片数量 2、默认最小分区数 同上，将最小分区数取默认最小分区数

5. 依赖关系

因为RDD是懒加载（lazy）机制的，子RDD会依赖父RDD，因此产生依赖。

基于迭代器设计模式

为文件设定一个起始锚点，有应用程序进来时，就new一个迭代器，通过迭代器去读文件；当有新的程序进来时，再new一个迭代器，避免并发操作导致的问题。

窄依赖

父RDD的分区最多会被子RDD的一个分区使用（一对一）

宽依赖

父RDD的一个分区会被子RDD的多个分区使用或父RDD的多个分区会被子RDD的一个分区使用（多对多） 数据容错方面窄依赖会优于宽依赖。

Stage划分

Spark中，每个对RDD的操作都会生成一个新的RDD，将这些RDD链接起来就会形成一个DAG。
​
Spark会根据DAG将整个任务划分为多个阶段（Satge）,每个stage有多个task，每个task作用在一个分区上；
一个stage的总Task数量是由最后一个RDD的分区个数决定的。
Stage的划分依据是是否有宽依赖，即是否有Shuffle

Shuffle（全局操作就会产生）

Spark之所以出现Shuffle，主要是因为具有某种共同特征的一类数据需要最终汇聚到一个计算节点上进行计算。 这些数据分布在各个存储节点上，并且由不用的计算单元进行处理。这种数据打乱然后汇聚到不同节点的过程就是Shuffle。 简单理解，当需要对所有数据进行全局分组、聚合、排序时，就需要经过shuffle了。 全局操作主要指：分组、聚合、排序 大数据量全局分组、全局排序、重新分区【调大】一定会经过shuffle过程。

#1.重新分区
repartition

#2.全局排序
reduceByKey、groupByKey

#3.join操作
join

Spark Shuffle过程也叫作宽依赖过程，Spark不完全依赖于内存计算，面临以上问题时，也需要磁盘。
​
​1.1以前​的版本一直是采用Hash Shuffle的实现的方式
​1.1版本​时参考Hadoop MapReduce的实现开始引入Sort Shuffle
​1.5版本​时开始Tungsten钨丝计划，引入UnSafe Shuffle优化内存及CPU的使用
​1.6版本​中将Tungsten统一到Sort Shuffle中，实现自我感知选择最佳Shuffle方式
​2.0版本，Hash Shuffle已被删除，所有Shuffle方式全部统一到Sort Shuffle一个实现中。

  • 功能：分区、排序、分组
  • 阶段：Shuffle Write 和 Shuffle Read
    • Shuffle Write：类似于Map端Shuffle过程，将当前Stage的结果进行分区、排序后写入HDFS
    • Shuffle Read：类似于Reduce端Shuffle过程，读取上一个Stage的结果，进行排序、分组等操作
  • 流程
    • Sort Shuffle：类似于MapReduce Shuffle的Shuffle过程，Spark1.2以后默认的Shuffle类型
    • Shuffle Write
    • Stage输出的结果先写入内存缓冲区
      • 内存中排序以后，生成小文件
      • 小文件合并成整体有序的大文件以及索引文件
    • Shuffle Read：根据算子的功能来实现，不同算子在Shuffle Read阶段实现的过程不同

  • 2-申请的内存=当前的数据内存情况*2-上一次的内存情况。
    • 如果达到临界阈值的话，则将内存数据结构中的数据溢写到磁盘，然后清空内存数据结构。
  • 3-排序：在溢写到磁盘文件之前，会先根据key对内存数据结构中已有的数据进行【排序】。
  • 4-溢写磁盘：排序过后，会分批将数据写入磁盘文件。默认的batch数量是10000条，也就是说，排序好的数据，会以每批1万条数据的形式分批写入磁盘文件。
  • 5-合并：对上面的小文件进行合并成1个文件，在索引文件中的start offset与end offset表示文件索引

ByPass机制（无需排序）

  • 就是无需排序了
  • 需要满足下面2点才会触发bypass机制：
  • 当shuffle 的reducetask的数量小于等于参数【spark.shuffle.sort.bypassMergeThreshold】的值时(默认为【200】)
  • 且算子不能是【带有map端预聚合的算子】。
    • reduceByKey是带有map端聚合的shuffle算子。（不会走bypass机制）
    • groupBykey（只分组不聚合）不是map端聚合的shuffle算子。（有机会走bypass机制）

6. 容错机制和持久化

容错机制分类

容错，也就是具有容忍程序出现异常。 容错机制一般有任务容错和数据容错。 而任务运行，有时候会因为一些不可抗力因素等（如资源不足、操作失败等），导致任务运行失败。是一种正常现象。 但是，在离线计算中，如果任务出现异常，最坏的结果无非是重新运行。 因此，我们一般不会过多关注任务的容错。而把重点关注在数据容错上。

数据容错方案

目的：保证数据安全。 思考：大数据中，常用的保证数据安全的方式有哪些？

  • 日志文件：将内存变化操作日志追加记录在一个文件中，下一次读取文件对内存重新操作。

如HDFS的edits文件，保证HDFS内存元数据的安全的。

  • 副本机制：将数据构建多份冗余副本

如HDFS的副本机制，保证HDFS数据的安全。

  • 依赖关系：每份数据保留与其他数据之间的一个转换关系

RDD的容错

每个RDD在构建数据时，会根据自己来源一步步倒推到数据来源，然后再一步步开始构建RDD数据，如下：

# step1: 构建RDD
rdd_test = sc.textFile("HDFS上的文件")

rs_rdd = rdd_test
		.filter 		# 过滤操作得到一个filter_rdd
		.flatmap		# 降维操作得到一个flatMap_rdd
		.map			# 转换操作得到一个map_rdd
		
# step2: 调用RDD
rs_rdd.foreach(lambda x: print(x)) # 触发job
rs_rdd.first # 触发job
rs_rdd.count # 触发job

当RDD的数据被触发调用时，就会根据RDD的血缘关系层层构建RDD的数据 如果在计算过程中，RDD的数据丢失，就会通过依赖关系重新构建，彻底保证了RDD的数据安全。 结论：Spark通过RDD的血缘进行容错。 思考：如果一个RDD被触发多次，这个RDD就会按照依赖关系被构建多次，性能相对较差，怎么解决？

RDD的容错机制 - persist缓存机制

问题：RDD依赖血缘机制保证数据安全，那每调用一次RDD都要重新构建一次，调用多次时性能就特别差，怎么办？ 解决：将RDD进行缓存，如果需要用到多次，将这个RDD存储起来，下次用到直接读取我们存储的RDD，不用再重新构建了

cache

  • 功能：将RDD缓存在内存中
  • 语法：cache()
  • 本质：底层调用的还是persist（StorageLevel.MEMORY_ONLY），但是只缓存在内存，如果内存不够，缓存会失败
  • 场景：资源充足，需要将RDD仅缓存在内存中

persist

  • 功能：将RDD【包含这个RDD的依赖关系】进行缓存，可以自己指定缓存的级别
  • 语法：persist(StorageLevel)
  • 级别：StorageLevel决定了缓存位置和缓存几份
# 缓存在磁盘中：注意这不是HDFS
StorageLevel.DISK_ONLY = StorageLevel(True, False, False, False)
StorageLevel.DISK_ONLY_2 = StorageLevel(True, False, False, False, 2)
StorageLevel.DISK_ONLY_3 = StorageLevel(True, False, False, False, 3)

# 缓存在内存中
StorageLevel.MEMORY_ONLY = StorageLevel(False, True, False, False)
StorageLevel.MEMORY_ONLY_2 = StorageLevel(False, True, False, False, 2)

# 缓存在内存中，如果内存不足就写入磁盘
StorageLevel.MEMORY_AND_DISK = StorageLevel(True, True, False, False)
StorageLevel.MEMORY_AND_DISK_2 = StorageLevel(True, True, False, False, 2)

# 缓存在堆外内存中：不是Executor内存
StorageLevel.OFF_HEAP = StorageLevel(True, True, True, False, 1)

# 缓存在内存中，如果内存不足就写入磁盘并且不经过序列化
StorageLevel.MEMORY_AND_DISK_DESER = StorageLevel(True, True, False, True)
  • 推荐：实际工作中一般推荐使用以下两种
StorageLevel.MEMORY_AND_DISK
StorageLevel.MEMORY_AND_DISK_2
  • 场景：根据资源情况，将RDD缓存在不同的地方或者缓存多份

unpersist

  • 功能：将缓存的RDD进行释放
  • 语法：unpersist
    • unpersist(blocking=True)：等释放完再继续下一步
  • 场景：明确RDD已经不再使用，将RDD的数据从缓存中释放，避免占用资源
  • 注意：如果不释放，这个Spark程序结束，也会释放这个程序中的所有内存
  • 测试
    • 没有缓存：每次需要重新构建
    • 配置缓存
# step3: 保存结果
# 对RDD进行缓存
# rs_rdd.cache() # 只缓存在内存中
rs_rdd.persist(StorageLevel.MEMORY_AND_DISK)
# 打印结果：构建RDD
rs_rdd.foreach(lambda x: print(x))
# 打印第一行：重新构建一遍
print(rs_rdd.first())
# 统计行数：重新构建一遍
print(rs_rdd.count())

# todo:3-关闭SparkContext
time.sleep(10000)
# 如果这个RDD明确后续代码中不会再被使用，一定要释放缓存
rs_rdd.unpersist(blocking=True)

小结：

问：cache和persist的区别？

cache：缓存在内存，底层调用的是persist算子
persist：数据可以缓存在内存或者磁盘，可以自己自定义缓存级别。
缓存级别：内存MEMORY、磁盘DISK、内存&磁盘MEMORY_AND_DISK

RDD容错机制 - checkpoint机制

Checkpoint机制，也称为检查点机制。 问题：为了避免重复构建RDD，可以将RDD进行persist缓存，但是如果缓存丢失，还是会重新构建RDD，如果有1个RDD，会被使用多次，要经过非常复杂的转换过程才能构建，我们不希望该RDD丢失，怎么解决？ 解决：给RDD设置检查点。

checkpoint

  • 功能：将RDD的数据【不包含RDD依赖关系】存储在HDFS上
  • 语法
# 设置一个检查点目录
sc.setCheckpointDir("../data/chk/")
# 将RDD的数据持久化存储在HDFS
rs_rdd.checkpoint()
  • 注意：在代码中会专门多一个job，用于构建数据
  • 场景：高安全性，适合对RDD的数据安全性要求比较高，对性能要求不是特别高的情况下
  • 思考：RDD的persist和checkpoint有什么区别？
#1.存储位置不同
	Persist：利用Executor的内存和节点磁盘来存储
	Checkpoint：利用HDFS存储
	
#2.生命周期不同
  	Persist：如果程序结束或者遇到了unpersist，内存和磁盘中的缓存会被清理
  	Checkpoint：只要不手动删除HDFS，就一直存在
  	
#3.存储内容不同
  	Persist：缓存整个RDD，保留RDD的依赖关系
  	Checkpoint：存储是RDD的数据，不保留RDD的依赖关系

总结

Spark的容错是依据RDD来容错的，RDD的完整的容错机制，RDD的某个分区的数据如果丢失，则先去内存找回数据，如果内存没有，则去磁盘寻找，

如果磁盘没有则去HDFS找，如果HDFS也没有，则从头计算出这部分数据。

7. 共享变量的使用

广播变量（解决共享变量读的问题）

功能：将一个变量元素进行广播到每台Worker节点的Executor中，让每个Task直接从本地读取数据，减少网络传输IO 特点：只读，executor端不能修改，目的是为了保证每个executor读到的内容都一致。

累加器（解决共享变量写的问题）

  • 累加器能保证在 Spark 任务出现问题被重启的时候不会出现重复计算
  • 累加器在全局唯一的，只增不减，记录全局集群的唯一状态；
  • 提供了将worker节点的值聚合到Driver的功能，可以用于计数和求和。
  • 累加器只能在Driver端定义，序列化到executor，在Executor端执行和修改；executor端不能读取累加器的值，需要在Driver端使用value属性获取。
  • 累加器只有在 Action 执行的时候才会被触发

使用场景：

  • 需要对共享变量进行修改
  • 对同一个rdd需要遍历多次计算多个指标
